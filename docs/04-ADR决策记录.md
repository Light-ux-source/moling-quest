## ADR-001 异步任务 + HTTP 轮询

**背景**：生成一组题需要 10–40 秒；微信 `wx.request` 默认 60 秒上限，同步请求在弱网下极易超时。

**决策**：`POST /sessions` 立即返回 202 和 session_id，后台任务生成；客户端每 1.2 秒轮询状态与进度。

**备选**：同步长请求；SSE；WebSocket。

**后果**：+ 实现简单、弱网稳、无长连接成本；− 有 1.2 秒感知延迟，请求量随 QPS 放大。**重审条件**：日活 > 1 万或轮询 QPS 成为瓶颈，改 SSE/降低频率。

## ADR-002 MVP 不做登录

**背景**：登录会引入用户表、openid、JWT、隐私协议、会话过期，均不服务于"生成质量"验证。

**决策**：用 session_id 标识一次学习，最近记录存本地；M4 再接微信登录与迁移。

**后果**：+ 开发快、可先内测；− 换设备不同步、无法按人防刷。**重审条件**：M4 上线前必须补登录与配额。

---

## ADR-003 客观题规则判分，简答 LLM

**背景**：全量 LLM 判分成本高、延迟大，且客观题有确定答案，用模型反而引入不确定性。

**决策**：单选/判断精确匹配；多选集合比较并给部分分；简答按 rubric 由 LLM 判，失败降级要点覆盖率。

**后果**：+ 快、稳、省；− 简答仍有波动。**重审条件**：简答占比 > 50% 或投诉率上升，考虑双模型复核。

---

## ADR-004 三道校验

**背景**：模型输出不可控，错误题目会直接摧毁信任。

**决策**：Prompt 强约束 → JSON mode + 容错解析 → Pydantic + 业务归一化（选项/答案/题型/来源白名单/去重），非法题直接丢弃。

**后果**：+ 脏数据不进入用户视野；− 可能少于请求题数。**重审条件**：丢弃率 > 20% 时需优化 Prompt 或换模型。

---

## ADR-005 SQLite 起步

**背景**：MVP 日活 < 100，QPS 极低，需要零运维与可复制备份。

**决策**：SQLite + WAL；所有 SQL 收敛在 `db.py` 仓储层，后续换 PostgreSQL 不动业务层。

**后果**：+ 零部署、单文件；− 并发写弱。**重审条件**：出现 `database is locked` 或需要多实例。

---

## ADR-006 Mock 双模式

**背景**：AI 依赖是最大不确定项；没有 Key、额度用尽、模型故障都会阻塞开发与演示。

**决策**：无 Key 自动 Mock；`LLM_PROVIDER=auto|deepseek|mock`；Mock 也走完整链路与同一套契约。

**后果**：+ 前后端解耦、可离线演示；− Mock 质量不代表真实效果，必须真实联调验收。

---

## ADR-007 报告存 JSON 快照

**背景**：报告是"当时的结论"，题目与判分后续可能变化。

**决策**：报告生成后整体存 `reports.payload`，不实时重算。

**后果**：+ 可复现、查询快、可分享；− 题目修改不回写历史报告（可接受）。

---

## ADR-008 原创猫灵替代官方 IP

**背景**：罗小黑是受版权保护的角色；未经授权使用形象/剧照有法律风险，且不利于长期品牌。

**决策**：只提取"黑猫 + 森林 + 墨色 + 陪伴"的意境，原创吉祥物「墨团」；全部 CSS/SVG 绘制。

**备选**：官方素材占位（仅内部）；购买授权；无吉祥物。

**后果**：+ 可商用、可自由延展；− 少了现成 IP 认知。**重审条件**：获得正式授权后可另做联名皮肤，但不替换主形象。

---

## ADR-009 治愈手绘纸感

**背景**：三种方向——治愈手绘纸感 / 童趣涂鸦贴纸 / 水墨国风留白。

**决策**：以纸感为底，苔绿 + 琥珀 + 朱砂；保留轻微不完美（微旋转、墨线），但不做高饱和大色块。

**理由**：最接近《罗小黑》"日常与森林"的气质；学习场景需要低刺激、长时间不疲劳；与多邻国式高饱和形成差异。

**后果**：+ 品牌辨识度、耐看；− 游戏化冲击力弱，需要靠星级/动效补。**重审条件**：若完赛率低且用户反馈"太素"，再增加贴纸化组件（不换底色）。

---

## ADR-010 章节地图 + 逐关解锁

**背景**：自由选题池更轻，但缺少"路径感"与回访理由。

**决策**：章节地图 + 6 关 + 章末综合关（需 3 星）；AI 生成的新主题作为一个新章节。

**后果**：+ 目标清晰、可讲故事；− 需要章节/进度模型与更多接口。**重审条件**：若用户更偏好自由练习，保留地图但增加"自由模式"。

---

## ADR-011 三星 60/80/100 + 不做失败羞辱

**背景**：星级能提供即时反馈，但过度惩罚会打击初学者。

**决策**：60% 一星、80% 二星、100% 三星；未达标不显示"失败"，文案改为"再走一遍"，主按钮"重练本关"。

**后果**：+ 友好、适合兴趣型用户；− 挑战感略弱。**重审条件**：硬核用户占比上升时增加"精英关"（独立标识）。

---

## ADR-012 AI 造关先预览后开始

**背景**：AI 生成质量不稳定，直接开答会让用户承担试错成本。

**决策**：先生成章节初稿，展示题干与题型、来源，用户可重新生成一次，再开始。

**后果**：+ 信任与可控；− 多一步操作、多一次等待。**重审条件**：生成质量稳定后提供"跳过预览"设置。

---

## ADR-013 不做深色模式

**背景**：纸白是这套视觉的根基；深色需要重做纸纹、墨线、琥珀对比与吉祥物阴影。

**决策**：MVP 只做浅色；`prefers-color-scheme` 不响应。

**后果**：+ 维护成本低、视觉统一；− 夜间体验弱。**重审条件**：夜间使用占比 > 25% 且用户明确要求。

---

## ADR-014 字体 CDN + 系统回退

**背景**：中文字体文件大，小程序加载外部字体需 HTTPS + CORS，容易阻塞首屏。

**决策**：H5 用 Google Fonts（`display=swap`）；小程序优先系统楷体/宋体回退；后续可托管子集字体。

**后果**：+ 首屏不被字体阻塞；− 不同设备字形有差异。**重审条件**：品牌一致性要求提高时，做 200–400 常用字子集。

---

## ADR-015 文档单一事实来源

**背景**：需求、方案、UI、页面说明、聊天记录容易各说各话。

**决策**：建立 `docs/` 文档中心，明确每类信息的唯一负责文档；冲突时按"需求 > UI > 实现"处理；代码 PR 涉及行为变化必须同步文档。

**后果**：+ 可维护、可交接；− 写文档有成本。**重审条件**：团队 > 3 人时引入文档评审流程与模板。

## ADR-016 LangChain 编排 Prompt（0.3.x + ChatDeepSeek）

**背景**：Prompt 逐步增多（digest / generate / grade / report），需要模板化、可组合、可替换模型，并保留 JSON 解析与 token 统计。原实现用 httpx 手写请求，Prompt 是 f-string。

**决策**：引入 LangChain `langchain-core 0.3.86` + `langchain-deepseek 0.1.4`，用 `ChatPromptTemplate` + LCEL 编排四条链；真实模型用 `ChatDeepSeek`，离线模式用自定义 `MockChatModel`，两条路径共用同一条链。

**版本约束**：LangChain 1.x 要求 Python ≥3.10；`langchain-deepseek 0.1.4` 与 1.x 的 `langchain-core` 冲突（实测 ResolutionImpossible）。本项目当前 Python 3.9，锁定 0.3.x 稳定线；升级 Python 3.12 后可重审是否切 1.x（改用 `ChatOpenAI` 走 DeepSeek OpenAI 兼容协议）。

**后果**：+ Prompt 与模型解耦、离线/真实同构、便于评测；− 多一层依赖与版本锁定；JSON 容错、空 content 重试仍由业务层兜底。

## ADR-017 一次生成 = 一章，5 题 = 5 个地图节点

**背景**：原型中 S02 为 6 节点、S08 为 5 关、S03 为 3/5、S04 为 80% 正确率，存在语义冲突。

**决策**：一次 AI 生成产出一个章节（5 题）；每题对应一个地图节点；第 6 节点为“章末 · 综合”，需前 5 关均 3 星后按需再生成 3 题。S03 的 5 个圆点即 5 个节点；S04 为章节结算。节点星级：答对 3 星、部分分 1 星、答错 0 星；章节星级按 60/80/100 阈值。

**后果**：+ 与 S08“5 关小章节”和 S03 5 个圆点一致；+ 一次生成即可开玩；− 章末综合需要额外一次生成，作为 P1 能力。

## ADR-018 匿名设备 ID 隔离章节/统计

**背景**：MVP 不做登录，但 S01/S02 的章节列表、S04 的段位、S05 的报告需要按用户隔离，不能全站共享。

**决策**：前端生成 `client_id` 存本地，所有请求带 `X-Client-Id`；后端在 `sessions/chapters` 落 `client_id`，章节/统计按它过滤；`session_id` 仍是单次学习的凭证。M4 接入 openid 后把 `client_id` 迁移绑定。

**后果**：+ 无登录也能有“我的章节/我的报告”；− 换设备不同步；− 清理与防刷仍需登录或配额。

## ADR-019 用 SVG 资源文件而不是 JSX 内联 SVG

**背景**：原型大量使用内联 SVG（墨团、图标、地图路径）；Taro 小程序端不支持在 JSX 中直接渲染 `<svg>`，但微信 `<image>` 官方支持 JPG/PNG/SVG/WEBP/GIF。

**决策**：`scripts/gen_assets.py` 从原型 SVG 生成 `src/assets/{icons,mascot,map}/*.svg`，通过 `<Image src="/assets/...">` 使用；构建时用 Taro `copy` 把资源复制到 `dist/assets` 与 `dist-h5/assets`。SVG 不使用 `<style>`、百分比单位；纸纹用 96×96 PNG base64。

**后果**：+ 视觉与原型一致、双端可运行；− 图标颜色需预生成变体；− 微信 SVG 对 text/style/百分比支持有限，生成脚本已规避。

## ADR-020 微信登录 + 游客 1 组试用 + 每日配额

**背景**：MVP 的无登录方案导致换设备丢失、无法按人控成本、无法合规注销。人工确认改为微信登录，且“不登录不得使用生成”需要兼顾首次转化。

**决策**：微信一键登录，首次自动注册；游客累计可试用 1 组，之后必须登录；登录用户 3 组/日（Asia/Shanghai 重置）；VIP 10 组/日仅预留；失败重试不重复扣、整组失败返还；游客数据在首次登录时 claim 到账号。开发/验收用 `/auth/dev`，生产禁用。

**后果**：+ 账号级同步、可审计、可注销；+ 保留 1 组体验降低门槛；− 登录依赖 AppSecret；− 游客清缓存可能绕过试用（IP/设备兜底有限）；− 配额并发“先查后建”可能多放行 1 组，后续用额度流水收敛。

**替代**：ADR-002（MVP 不做登录）与 ADR-018（纯 client_id 隔离）在本期被扩展，而非删除；历史决策保留。

## ADR-021 数据库从 SQLite 切换为 MySQL

**背景**：人工要求数据库改为 MySQL；后续多实例、并发写入与运维备份需要网络数据库。

**决策**：`backend/app/db.py` 全量改为 PyMySQL 仓储；表使用 `utf8mb4`；启动时 `CREATE TABLE IF NOT EXISTS` + 只加列/索引迁移；开发用独立 3307 实例脚本，生产配置 `MYSQL_*` 指向 MySQL 8+/9。

**后果**：+ 可多实例/集中备份；+ 与生产形态一致；− 本地多一个 MySQL 进程；− 需 `cryptography` 支持 caching_sha2_password；− 旧 SQLite 数据不自动迁移，需重新 seed 或一次性脚本。

**重审条件**：QPS/并发显著上升时评估连接池、读写分离；若改用 PostgreSQL，只需替换仓储实现。
